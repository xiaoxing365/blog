一、用户管理：让该进来的人进来

数据库装好之后，不能所有人都用 root 为所欲为。给每个应用、每个人分配独立账号，是安全的第一步。MySQL 里的账号不是光写一个用户名就完事，而是由”用户名 + 允许登录的主机”共同组成，写作 '用户名'@'主机'。同一个用户名，来自不同主机的连接会被当作不同账号对待。

二、角色：MySQL 8.0 的权限批量管理工具

角色是 MySQL 8.0 引入的新特性，可以把它理解为”权限的容器”。用生活化的类比：用户是员工（能登录系统），角色是职位（比如财务、管理员），权限是能做的事情（比如查看工资表）。一个员工可以担任多个职位，从而拿到对应的权限；给十个人配相同的权限，不必重复执行十条 GRANT，只要把角色分配给这十个人即可。MySQL 5.7 没有角色功能，只能逐个用户授权。

2.1 用户与角色的主要区别

特性 用户（User） 角色（Role）
能否登录 可以，需要用户名和密码 不能，没有密码，仅用于权限管理
能否被授予权限 可以 可以，作为权限集合
能否被多个对象复用 不能被其他用户继承 可以分配给多个用户
主机限制 支持 'user'@'host' 格式 同样支持 'role'@'host' 格式
是否需要激活 不适用 用户获得角色后通常要激活才生效

三、权限授予与回收

3.1 查看已有权限

结果里通常能看到一条 USAGE，它不代表真的有权限，只是说明账号可以连接。

3.2 授予权限 GRANT

  • ALL PRIVILEGES 表示所有权限。
  • *.* 中第一个 * 是所有库，第二个 * 是所有表；company.* 表示 company 库下的所有表。
  • WITH GRANT OPTION 允许该用户再把自己的权限转授给别人，风险很高，除非必要不要给。

3.3 让权限变更生效 FLUSH PRIVILEGES

要解决什么：当直接用 UPDATE、DELETE 改写了 mysql.user 等系统表时，内存中的权限缓存不会自动更新，需要 FLUSH PRIVILEGES 重新加载。通过 GRANT、REVOKE、CREATE USER 这类标准语句做的改动，MySQL 一般会自动生效，但执行一下也无妨，是常见的安全习惯。

3.4 核心权限精简表

MySQL 的权限种类很多，日常真正高频使用的其实是下面这些：

权限 作用资源 说明
Select 表 读取数据，最常用
Insert 表 向表中新增数据行
Update 表 修改表中已有数据
Delete 表 删除表中的数据行
Alter 表 修改表结构，比如加字段
Index 表 创建或删除索引
Create 库、表 新建数据库和表
Drop 库、表 删除数据库、表或视图
Grant option 库、表、函数、存储过程 决定能否把权限再授予他人
Usage 服务器管理 没有任何实质权限，只保留连接资格

还有三个特殊点值得单独记住：Usage 是所有用户天然自带的”仅能连接”权限；ALL 表示管理员身份的绝大多数权限，但不包含 Grant option；Grant option 必须单独授予，是 root 把转授权能力交给别人的开关。

完整权限清单（包括各类服务器管理、复制、审计、加密相关权限）内容很多，本文不逐一罗列，请以 MySQL 官方文档为准：https://dev.mysql.com/doc/refman/8.0/en/privileges-provided.html 。

3.5 回收权限 REVOKE

库名和表名都可以用 * 通配，写法与 GRANT 一致。REVOKE ALL PRIVILEGES 可以一次性收回全部权限。

七、sys Schema 性能诊断入门

数据库变慢时该从哪里下手？MySQL 5.7 引入的 sys schema 就是官方给的”仪表盘”。它本身不采集数据，而是把 performance_schema 和 information_schema 里那些复杂难懂的性能数据，包装成更易读的视图、函数和存储过程，让性能诊断变得直观。

7.1 视图分类速览

sys 里的视图分两类：友好格式视图（如 host_summary）会把时间、字节换算成毫秒、GB 等易读单位；以 x$ 开头的原始视图（如 x$host_summary）提供皮秒、字节级别的原始数据，留给工具程序处理。

类别 说明 常用视图举例
主机相关 按客户端 IP 汇总资源消耗 host_summary、host_summary_by_file_io
用户相关 按用户汇总资源与语句统计 user_summary、user_summary_by_statement_latency
InnoDB 相关 缓冲池状态与锁信息 innodb_buffer_stats_by_schema、innodb_lock_waits
I/O 相关 文件 I/O 使用情况 io_global_by_file_by_bytes、io_global_by_wait_by_latency
内存相关 多维度内存使用 memory_by_host_by_current_bytes、memory_global_total
语句相关 SQL 执行情况，优化重点 statement_analysis、statements_with_full_table_scans
库表相关 表与索引统计 schema_table_statistics、schema_index_statistics
会话与进程 增强的会话、进程列表 session、processlist

7.2 几个立刻能用的诊断查询

要解决什么：慢 SQL、冗余索引、锁等待是三类最常见的问题，sys 里都有现成视图，直接查即可。

预期效果：不用手写复杂的 performance_schema 联表查询，就能快速定位问题方向。比如第一条结果里出现了某条 SELECT，就优先考虑为它的 WHERE 条件建索引。

7.3 使用前提与性能开销

sys 的数据来自 performance_schema，因此要确保 performance_schema=ON，这是现代 MySQL 的默认设置。sys 视图本身是只读的，查询开销很小；但底层 performance_schema 开启后要持续收集大量性能数据，有资料提到可能带来约 10% 的性能影响。考虑到它带来的可观测性，这点开销在多数场景下是值得的。详细内容可参考 MySQL 5.7 官方手册：https://dev.mysql.com/doc/refman/5.7/en/sys-schema.html 。

小结

权限、备份、诊断是数据库稳定运行的三根支柱。用户用 '用户名'@'主机' 精确界定身份，8.0 的角色让批量授权变得轻松；GRANT 与 REVOKE 负责权限的收放，核心权限表覆盖了日常绝大多数需求，完整清单查官方文档。数据层面用 mysqldump 做逻辑备份，配合 source 或 LOAD DATA LOCAL INFILE 恢复。万一忘记 root 密码，跳过权限校验登录后按版本改密即可，但要记得限制连接方式。最后，遇到性能问题别急着瞎调参数，先用 sys Schema 把慢 SQL、冗余索引和锁等待找出来，再针对性优化。
