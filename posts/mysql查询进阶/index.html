一、从一张表开始：单表查询与 CRUD

把数据库想成一个管理有序的仓库：库（database）是厂房，表（table）是一排排货架，行是货架上的一件件货，列则是每件货上的标签。写 SQL 无非就是”盖厂房、摆货架、放货、找货、改货、清货”这几件事。本节先只作用于一张表，把最常用的语句走一遍。

1.1 创建数据库与数据表，以及常见数据类型

动手之前先有地方放数据。

创建表时要为每个字段指定数据类型，类型选得合适，既省空间又避免诡异错误。

要解决什么：字段类型决定了能存什么、占多少空间。把字符串一律写全 VARCHAR(255) 看似省事，其实会浪费内存和索引空间；该存日期的字段用字符串，后面按时间范围查询就会很痛苦。

常见数据类型速查：

数据类型 含义 典型用途
int / integer 整数类型 编号、年龄、数量
float 单精度浮点数 精度要求不高的近似小数
double 双精度浮点数 比 float 精度更高的小数
char 定长字符串 性别、状态码等长度固定的短值
varchar(n) 最长 n 个字符的变长字符串 姓名、标题、地址
text 最长约 64KB 的大文本（再长用 MEDIUMTEXT / LONGTEXT） 文章内容、备注
date 日期，格式 YYYY-MM-DD 生日、入职日
time 时间，格式 HH:MM:SS 打卡时间
year 年份，格式 YYYY 成立年份
datetime 日期+时间，YYYY-MM-DD HH:MM:SS 创建时间、支付时间

像 int(10) 这种括号里的数字只是显示宽度，并不限制能存多大整数（整数范围由类型本身决定），实际开发中通常没必要写。AUTO_INCREMENT 必须用在有索引的列上，一般配合主键使用，插入时不给值就会自动递增。

1.2 CRUD：增删改查四件套

CRUD 就是 Create（增）、Read（查）、Update（改）、Delete（删）的缩写，是最基本的四类操作。

预期效果：INSERT 添加一条记录，SELECT 把它读出来，UPDATE 修改工资，DELETE 移除指定行。一个高频事故是 UPDATE 或 DELETE 忘了写 WHERE——执行前先在脑子里过一遍”条件命中几行”，必要时先用相同条件的 SELECT 确认范围。

这里顺便区分两个”删除”：DELETE FROM 表名 是清空表里的数据行，表结构还在，可以配合 WHERE 按条件删；DROP TABLE 表名 是把整张表连同结构一起删掉，表就没了。要特别注意：DROP TABLE 不支持 WHERE 子句，只有 DELETE 才支持，别把两者混用，这个细节要记牢。

1.3 WHERE 条件与 LIKE 模糊匹配（% 通配符）

精确查找用 =，范围查找用比较运算符，而”包含某个关键词”这类需求要靠 LIKE。

要解决什么：当搜索词只有一部分时，比如”找出姓名里带’小’的人”，等值匹配无能为力，LIKE 配合通配符就能搞定。% 是通配符，表示”任意长度的字符”，不要把它误当成正则表达式——LIKE 的模式语法和正则完全是两回事。

1.4 UNION 合并多个结果集

当两张结构相同的表要合并展示，或者同一个表的两类筛选结果要拼在一起，就用 UNION。

预期效果：返回两个 SELECT 结果的并集。前提是上下两段查询的列数必须一致，对应列的类型也要兼容。UNION 默认去掉重复行，如果确认不需要去重，用 UNION ALL 更快。

1.5 ORDER BY 排序

预期效果：先按工资从高到低排，工资一样的再按入职时间从早到晚排。ASC 是升序（默认），DESC 是降序。排序可以指定多列，用逗号隔开，每一列各自决定升降。

1.6 GROUP BY 分组与 WITH ROLLUP 汇总

分组用于”按某个维度统计”，比如每个部门多少人、每个城市销售额多少。

要解决什么：分组把相同 dept_id 的行聚成一组，COUNT、SUM、AVG 这类聚合函数分别对每组计算。加上 WITH ROLLUP 后，数据库会在最后多出一行”所有组合计”，做报表时特别方便。注意 SELECT 列表里的普通列要么出现在 GROUP BY 中，要么被聚合函数包住，否则结果没有意义。分组前筛行用 WHERE，分组后筛组用 HAVING。

1.7 NULL 的判断：为什么 = NULL 不工作

NULL 表示”未知/没有值”，它不是 0，也不是空字符串。在 SQL 里 NULL = NULL 的结果既不是 true 也不是 false，而是”未知”，所以用 = 判断 NULL 永远查不出东西。

预期效果：能正确找出工资未录入的员工。IS NULL、IS NOT NULL 和 <=> 是 MySQL 处理 NULL 的三大运算符，其中最常用的是前两个。注意表名与 WHERE 关键字之间要保留空格（不过 DROP TABLE 并不支持 WHERE 子句，见 1.2 节）。

1.8 ALTER TABLE 修改表结构

需求变了要加字段、改类型、改名字，都靠 ALTER TABLE。

预期效果：表结构按命令逐项变更。MODIFY 只改类型不改名字，CHANGE 名字和类型一起改，两者别混用；生产环境改结构前先备份，避免误操作丢数据。

二、多表查询：JOIN 把分散的数据拼起来

真实业务里数据不会挤在一张表。员工表里存部门编号，部门表里存部门名称，要同时看到”员工姓名 + 部门名称”，就得把两张表按关联字段拼起来，这就是 JOIN。

2.1 四种 JOIN 的区别

连接类型 返回什么 语法骨架
INNER JOIN（内连接） 只返回两表中匹配成功的行 A INNER JOIN B ON A.key = B.key
LEFT JOIN（左连接） 返回左表全部行，右表没匹配上的补 NULL A LEFT JOIN B ON ...
RIGHT JOIN（右连接） 返回右表全部行，左表没匹配上的补 NULL A RIGHT JOIN B ON ...
FULL JOIN（全连接） 只要一边有匹配就返回 标准 SQL 有，MySQL 不直接支持，用 LEFT UNION RIGHT 模拟

2.2 主键与外键的区别

JOIN 之所以能关联，靠的是主键和外键这套”锚点”机制。

对比维度 主键（PRIMARY KEY） 外键（FOREIGN KEY）
作用 唯一标识表中的每一行 建立表与表之间的关系，保证引用完整性
唯一性 值必须唯一，不能重复 可以重复，多个行可以引用同一个主键
是否可为空 不能为 NULL 可以为 NULL，表示该行没有关联对象
数量限制 一张表至多一个主键（可由多列组成复合主键） 一张表可以有多个外键
稳定性 一旦确定就不应修改 可随业务关联变化而调整
典型例子 员工编号、学号 员工表的部门编号、订单表的用户编号

简单记：主键回答”我是谁”，外键回答”我属于谁”。主键所在的表叫主表（父表），外键所在的表叫从表（子表）。外键要求引用的值必须存在于主表对应列中，从而避免”部门编号 99 却找不到这个部门”这种脏数据。

2.3 字符集 utf8mb4 与”Incorrect string value”错误

表设计里还有个绕不开的话题：字符集。MySQL 里的 utf8 是个”精简版”，最多只支持 3 字节字符，而 emoji 表情、部分生僻字需要 4 字节；utf8mb4 才是真正的完整 UTF-8，它是 utf8 的超集，能存所有 Unicode 字符。简单说，utf8mb4 包含 utf8。

三、约束与设计：让数据自己”守规矩”

约束是写在表结构上的规则，数据库会替你挡住不合法的数据。MySQL 主要有六种约束。

3.1 六种约束速查

约束 名称 作用 典型场景
NOT NULL 非空约束 字段值不能为空 姓名、学号必须有
DEFAULT 默认值约束 不填值时自动填入预设值 性别默认”未知”、状态默认 0
PRIMARY KEY 主键约束 值唯一且非空，一张表最多一个 学号、员工编号
UNIQUE 唯一约束 值不能重复，可以有多个，允许为 NULL 座位号、手机号
CHECK 检查约束 检查字段值是否有效 年龄大于 0、性别只能是男女
FOREIGN KEY 外键约束 值必须来自主表关联列，维护一致性 员工表的部门编号

按作用范围又分列级约束和表级约束：NOT NULL、DEFAULT、PRIMARY KEY、UNIQUE、CHECK 可以直接写在字段后面当列级约束；PRIMARY KEY、UNIQUE、CHECK、FOREIGN KEY 也可以写在一行里用 CONSTRAINT 开头当表级约束。CHECK 约束在 MySQL 5.7 里只是语法上接受、实际不生效，8.0.16 起才真正执行。

预期效果：外键解除后，两张表的关联不再强制校验，此时才能安全地调整主键。原文关于”套娃式删除所有外键”的说法可以理解为：按依赖顺序从最末端的子表开始逐层解除，别试图一步到位。

小结

写 SQL 的能力可以分三层：第一层是单表 CRUD，配合 WHERE、LIKE、ORDER BY、GROUP BY 把一张表玩熟，尤其留意 NULL 要用 IS 判断、UPDATE/DELETE 必须带 WHERE；第二层是多表 JOIN，理解 INNER 取交集、LEFT/RIGHT 保单边，MySQL 没有原生 FULL JOIN 就用 UNION 拼；第三层是约束与表设计，用主键唯一标识、外键维护关系、六类约束兜底数据质量，再加上 utf8mb4 字符集避免乱码。三层都扎实了，查询的准确性和可维护性会有明显提升，后面学函数、视图和性能优化也会顺很多。
